# 문제 생성 JSON 오류 복구 (2026-11-25)

## 목표 / Goal
'이해도 확인'에서 실제 추론형 모델(GPT-6.1 Sol)로 SQLD 요약노트 5문제를 만들 때 `문제 형식을 해석하지 못했습니다: Expecting ',' delimiter: line 1 column 1920` 오류가 났다. 문제가 끝까지 나오게 하고, 실패해도 이해하기 쉽게 안내한다.

## 결정과 근거 / Decisions & Why
- **원인 (추정, 원문을 버리고 있어 확정 불가)**: ① `max_tokens=3000`. 추론형 모델은 숨은 추론 토큰까지 이 한도에 포함돼 JSON이 중간에 잘린다(2026-11-18 답변 잘림과 같은 원인). ② SQL 큰따옴표(`WHERE name = "kim"`)가 JSON 문자열을 깨뜨린다.
- **숨은 버그**: 검증 모델 정답 대조 한도가 300이었다. 추론형 모델이면 잘려서 모든 문제가 '검토 필요'가 되고, 오답노트 유사 문제가 전부 걸러질 수 있다. 1500으로 올렸다.
- **복구 단계**: 파싱 → (잘리지 않았으면) AI 복구 호출 1회 → 원문에서 온전한 문제만 살리기(`json.raw_decode`).
  - 잘렸으면 복구 호출을 하지 않는다. 사라진 내용을 되살릴 수 없고, 지어낼 위험만 있다.
  - 복구 호출이 실패하거나 빈 목록을 돌려줘도 원문에서 살린다.
  - 복구 호출은 실패했을 때만 일어나므로 평소에는 추가 비용이 없다.
- **사용자 안내**: 기술 메시지 대신 "N문제만 만들었어요, 다시 시도하면 …" 같은 쉬운 문구를 보여준다. 원인 확인용으로 'AI 원문 보기' 펼침을 둔다.
  - 사용자는 "오류를 AI가 설명"하길 요청했다. 대신 "AI가 형식을 고쳐서 문제가 나오게" 하는 방향을 제안했고, 사용자가 동의했다.
- **`generate()` 시그니처 유지**: 오답노트 유사 문제 생성(`wrongnote.make_similar`)도 같은 함수를 쓰므로 함께 개선된다. 이제 형식 오류로 예외를 올리지 않는다.

## 검증 / Cross-check
### Copilot 응답 전문
```
1. **중간** — 원문에서 문항을 살릴 수 있어도 복구 응답이 `{"questions":[]}`처럼 *유효한 빈 JSON*이면 원문 복구를 건너뜁니다. `parse_questions(fixed)`가 빈 목록을 반환해도 `qs is None`이 아니므로 `salvage_questions(raw)`가 실행되지 않습니다. 복구 결과가 비었을 때도 원문을 살리고, 실제 문항이 있을 때만 복구 성공으로 처리하세요.

2. **중간** — 결과가 요청 수보다 적어도 일부 경우 안내 없이 표시됩니다. 부분 복구가 유효한 JSON으로 끝나거나, 파싱 가능한 JSON에서 잘못된 문항만 걸러진 경우 `truncated`와 `salvaged`가 모두 거짓이라 안내문이 나오지 않습니다. `len(qs) < n`이면 원인과 관계없이 부족한 문항 수를 안내하고 원문 펼침을 표시하세요.

**고위험 이슈는 없습니다.**

```
### 분류
1. 복구 응답이 빈 목록이면 원문 살리기를 건너뜀 → **반영함**. 빈 목록은 복구 실패로 본다. 테스트 1개.
2. 문제 수가 모자라도 안내가 없는 경우가 있음 → **반영함**. 원인과 관계없이 `len < n`이면 안내한다. 테스트 1개.

## 함정 / Gotchas
- 모델에 JSON을 요청하는 호출은 모두 추론 토큰 때문에 잘릴 수 있다. 새 호출을 추가할 때는 한도를 넉넉히 잡고 `chat_with_status`로 잘림을 확인한다.
  - 남은 곳: `wrongnote.suggest_causes`의 800
- `salvage_questions`는 `"questions"` 키와 `[`가 있어야 동작한다. 모델이 다른 키 이름을 쓰면 살리지 못한다.
